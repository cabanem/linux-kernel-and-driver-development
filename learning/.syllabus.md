# Linux Kernel & Driver Development — Self-Study Syllabus

Oct 28, 2026 · @Emily Cabaniss

## Course overview

Nine units, each built around one concept and one project you can run. Written for someone with C++ experience and no kernel experience; by the end you will have written a complete driver for real hardware and sent a patch upstream.

**Pacing.** About 5–8 hours a week lands this in 6–8 months. Units 0–2 are short (a week or two each); Units 3–5 are the heavy middle; Units 6–8 go faster because by then you can read the tree.

**How each unit works.** Each has a concept, a reading assignment, a project, and an exit check. Do the project before finishing the reading — the kernel makes more sense when you have already been confused by it. Keep every project in one git repo, one directory per unit; later units reuse earlier code.

**One rule.** Do not skip ahead to the kernel build (Unit 4) before you have loaded a module (Unit 1). The module is the smallest thing that is actually kernel code, and it is the mental model everything else hangs on.

| Unit | Concept | Project | Approx. weeks |
| --- | --- | --- | --- |
| 0 | C the way the kernel writes it | `tinyalloc` + `klist` userspace exercises | 2 |
| 1 | Loadable modules | `hello` module with parameters and sysfs | 1–2 |
| 2 | Char devices, user/kernel boundary | `kfifo`-backed `/dev/pipe0` | 3 |
| 3 | Memory and concurrency | Make `/dev/pipe0` correct under contention | 4 |
| 4 | Build, boot, debug | Custom kernel in QEMU with KASAN/lockdep; deliberately crash it | 3 |
| 5 | Driver model, buses, device tree | Virtual platform device bound by DT | 4 |
| 6 | Interrupts, deferred work, time | Interrupt-driven virtual device in QEMU | 3 |
| 7 | Real hardware | I²C sensor driver on a Raspberry Pi, in the IIO subsystem | 6 |
| 8 | Contributing upstream | A merged staging or docs patch | 3+ |

## Lab setup

All kernel work happens in a Linux VM you are willing to destroy. Kernel bugs do not segfault; they take the OS down, so never develop against the machine you are typing on.

**Minimum (Units 0–3).** Any x86-64 Linux VM with 4 GB RAM and 20 GB disk: VirtualBox, Hyper-V, VMware, or a cloud instance. Debian or Ubuntu LTS keep the examples simple. Install `build-essential`, `linux-headers-$(uname -r)`, `git`, `gdb`, `strace`, and `clang-format`. WSL2 works for Unit 0 only; its kernel is custom and awkward for modules.

**Full (Unit 4 on).** Inside that same VM: a clone of `torvalds/linux` (or the current stable tree), `qemu-system-x86_64`, `busybox` for an initramfs, and `cscope` or `clangd` for navigating the tree. Nested virtualization helps but is not required; QEMU without KVM is slow but works. From Unit 5 on, add `qemu-system-aarch64` and an ARM cross-compiler, since the device-tree world is ARM.

**Hardware (Unit 7).** A Raspberry Pi 4 or 5 and one I²C sensor breakout (a BMP280 or similar, under $10). A USB-to-serial adapter for the Pi's console is the single most useful debugging purchase you will make.

**Debugging stack, built up over the course.** `printk`/`dmesg` from Unit 1; `CONFIG_DEBUG_KERNEL`, KASAN, lockdep, and `CONFIG_PROVE_LOCKING` from Unit 4; KGDB over QEMU's gdbstub and `ftrace` from Unit 6. Turn the debug options on early and leave them on; they catch the bugs you are about to write.

**Habits from day one.** Run `scripts/checkpatch.pl` on every file before you commit. Format with the kernel `.clang-format`. Write commit messages in kernel style (subsystem prefix, imperative subject, body explaining why). These are free to adopt now and expensive to retrofit in Unit 8.

## Unit 0 — C the way the kernel writes it

The goal is not C fluency in general; it is the specific dialect the kernel uses, which replaces every C++ convenience with a hand-built idiom. You will relearn polymorphism, cleanup, and error handling as patterns rather than language features.

**Concepts.** Struct embedding and `container_of()` as inheritance. Function-pointer structs as vtables. `goto`-unwind cleanup in place of RAII. Negative-`errno` returns and `ERR_PTR`/`IS_ERR` in place of exceptions. Intrusive linked lists (the node lives inside your struct, not the other way round). Compiler attributes and the `likely`/`unlikely`, `__must_check`, `__init` family. Integer promotion and the `sizeof` traps that bite C++ programmers.

**Reading.** K&R to the end, quickly. `Documentation/process/coding-style.rst` (short; read it twice). `include/linux/list.h` and `include/linux/container_of.h` — read the macros until you can explain why they work. Chapter 1 of Robert Love's *Linux Kernel Development*.

**Project: `klist` and `tinyalloc`, in userspace.**

1. Port the kernel's `list.h` to a userspace header and use it to build a task scheduler simulation: a struct `task` with an embedded `list_head`, round-robin iteration with `list_for_each_entry`, removal mid-iteration with the `_safe` variant. No `malloc` of list nodes — the node lives inside the task.
2. Write `tinyalloc`: a fixed-arena allocator with a free list, exposing an `ops` struct of function pointers (`alloc`, `free`, `stats`). Implement two backends (first-fit, bump) behind the same struct. This is the `file_operations` pattern before you meet `file_operations`.
3. Rewrite one function from each with full kernel-style error handling: every allocation checked, every failure unwinding through labeled `goto`s, and `checkpatch.pl --file` clean.

**Exit check.** You can read `struct file_operations` in `include/linux/fs.h` and explain what each pointer is for, and you can write `container_of` from memory and say why the `offsetof` trick is legal.

## Unit 1 — Loadable kernel modules

A module is code linked into the running kernel's address space with no safety net. Everything about modules — licensing, symbol exports, reference counts, the two-line Makefile — follows from that one fact.

**Concepts.** The module lifecycle (`module_init`/`module_exit`, `__init`/`__exit` sections and why their memory is freed). `printk` log levels and `pr_*` helpers. Module parameters and `/sys/module/<name>/parameters`. Symbol export (`EXPORT_SYMBOL`, `EXPORT_SYMBOL_GPL`) and the GPL taint. The out-of-tree build (`obj-m`, `KDIR`, `M=$(PWD)`) and what `modpost` does. sysfs: `kobject`, attributes, `show`/`store`.

**Reading.** *The Linux Kernel Module Programming Guide*, chapters 1–8. LDD3 chapters 1–2 (the build details are stale; the explanations are not). `Documentation/kbuild/modules.rst`. `Documentation/filesystems/sysfs.rst`.

**Project: `hello`, three times over.**

1. The 15-line module: load it, read `dmesg`, unload it. Then break it on purpose: remove `MODULE_LICENSE` and read the taint warning; put `__init` on a function called after init and watch it crash on a second call. Keep the oops text — you will learn to read it in Unit 4.
2. Add module parameters (an int, a string, a bool), set them at `insmod` time, change one at runtime through `/sys/module`, and have the module log when it changes.
3. Split it into two modules: `hello_core` exports a function; `hello_user` calls it. Load them in the wrong order and read the error. Then add a sysfs attribute to `hello_core` under `/sys/kernel/` with a `show` and a `store`, so `echo` into a file changes module state.

**Exit check.** You can explain what `insmod` does step by step (relocation, symbol resolution, init call), why `rmmod` can refuse, and what a reference count on a module protects against.

## Unit 2 — Character devices and the user/kernel boundary

A character device is where "everything is a file" becomes literal: you implement `file_operations`, and `cat`, `echo`, and `dd` become your test harness. The unit is really about the boundary — what crosses it, how, and what the kernel refuses to trust.

**Concepts.** Major/minor numbers, `alloc_chrdev_region`, `cdev_add`, and `device_create` so udev makes the `/dev` node for you. `file_operations`: `open`, `release`, `read`, `write`, `llseek`, `unlocked_ioctl`. `copy_to_user`/`copy_from_user` and why a raw pointer from userspace must never be dereferenced. `struct file` versus `struct inode` (per-open state versus per-device state), and `private_data`. `ioctl` number construction with `_IOR`/`_IOW`. Blocking I/O: wait queues, `wait_event_interruptible`, `O_NONBLOCK`, and `poll`.

**Reading.** LDD3 chapters 3, 5 (skim; Unit 3 covers it properly), and 6. LKMPG chapters 6–7 and 9. `Documentation/driver-api/driver-model/` for `device_create`. `Documentation/userspace-api/ioctl/` for the numbering rules.

**Project: `/dev/pipe0`, a kernel FIFO.**

1. A char device backed by a fixed buffer. `write` appends, `read` consumes, `cat` and `echo` work. Return the right counts and the right errors (`-ENOSPC`, `-EFAULT`, `-EINVAL`) and verify each with `strace`.
2. Make it block: a `read` on an empty buffer sleeps until a `write` arrives; a `write` on a full buffer sleeps until there is room. Support `O_NONBLOCK` (`-EAGAIN`) and `poll`, and prove it with a small userspace program that uses `select`/`poll` on your device. Note this project is deliberately single-reader, single-writer for now; it is not yet safe under contention.
3. Add `ioctl`s: query capacity, resize the buffer, clear it. Write the userspace header for them the way a real driver would (`include/uapi/`-style, `_IOR`/`_IOW` macros), and a tiny CLI that uses it.
4. Replace your buffer with the kernel's own `kfifo` and compare: what did you get wrong, and what does it not do for you?

**Exit check.** You can draw what happens between `read(fd, buf, 16)` in userspace and your `read` method being called, name every struct touched on the way, and explain why `copy_to_user` can fail and what you must do when it does.

## Unit 3 — Kernel memory and concurrency

The kernel is a single, multithreaded, preemptible program where every piece of your code can be interrupted, run on several CPUs at once, or run in a context where sleeping is a crash. This unit is the one that separates people who can write a module from people who can write a correct one.

**Concepts.** Process context versus atomic context, and which API calls may sleep. `kmalloc`/`kzalloc` and the GFP flags (`GFP_KERNEL` sleeps, `GFP_ATOMIC` does not). `vmalloc` versus `kmalloc`, slab caches, `devm_` managed allocations. Locking, in order of preference: lock-free (per-CPU, atomics, RCU), `spinlock_t` (never sleep while held), `mutex` (may sleep), `rwlock`/`rwsem`, `seqlock`. Why the IRQ-disabling spinlock variants exist. Reference counting with `kref`. Memory barriers at the level of "know they exist and when the locking API already provides them." Lockdep: what it can prove and what it cannot.

**Reading.** LDD3 chapters 5, 7, and 8. *Linux Kernel Development* chapters 9–12. `Documentation/locking/` (especially `locktypes.rst` and `lockdep-design.rst`). `Documentation/RCU/whatisRCU.rst`. `Documentation/core-api/memory-allocation.rst`. Paul McKenney's *Is Parallel Programming Hard?* chapters 1–4 for the mental model.

**Project: make `/dev/pipe0` correct.**

1. Write a userspace stress test: eight writers, eight readers, random sizes, with checksums so you can detect corruption and lost bytes. Run it against the Unit 2 driver and watch it fail (or oops).
2. Fix it with a mutex. Then measure: throughput with one lock around everything. Then split into reader and writer locks and measure again. Lockdep must stay silent throughout.
3. Add a `GFP_ATOMIC` path: a second `ioctl` that must work from a context that cannot sleep (you will fake that context with a timer callback — a preview of Unit 6). Observe what happens when you call a sleeping function from it with `CONFIG_DEBUG_ATOMIC_SLEEP` on.
4. Replace device-struct lifetime management with `kref`, so a reader holding the device open while the module is being removed does not use freed memory. Prove the bug exists first, then prove it is gone, with KASAN on.
5. Stretch: expose a read-mostly configuration struct through RCU, and explain in a paragraph why RCU is correct here and a mutex would be worse.

**Exit check.** Given any kernel function, you can say whether it may be called with a spinlock held and why. You can read a lockdep splat and name the lock-order inversion it is reporting.

## Unit 4 — Building, booting, and debugging the kernel

Building and booting a kernel yourself turns it from an artifact into a program. After this unit you will read oops messages the way you read stack traces today, and you will have a QEMU harness that boots a fresh kernel in seconds.

**Concepts.** The source tree layout and how to navigate it (`cscope`/`clangd`, `git log -S`, `git blame`). Kconfig and `.config`: `defconfig`, `menuconfig`, `localmodconfig`, and what a `CONFIG_` symbol becomes in C. Kbuild: how `obj-y`/`obj-m` in a `Makefile` turns into `vmlinux` and `.ko` files. The boot sequence from bootloader to `init`. An initramfs and why it exists. Reading an oops: the call trace, `RIP`, `addr2line`/`scripts/faddr2line`, `decode_stacktrace.sh`. KASAN, UBSAN, lockdep, `CONFIG_DEBUG_LIST`, `CONFIG_PROVE_LOCKING`. KGDB over QEMU's gdbstub. `ftrace` and `trace-cmd` for "what did the kernel just do." Dynamic debug (`dyndbg`).

**Reading.** *Linux Kernel in a Nutshell* (Kroah-Hartman; free online) for build and config. `Documentation/kbuild/kconfig-language.rst` and `makefiles.rst`. `Documentation/admin-guide/bug-hunting.rst` and `Documentation/dev-tools/` (KASAN, kgdb, ftrace). *Linux Kernel Development* chapters 18 and 20. Bootlin's *Linux kernel and driver development* slides, sections on kernel build and booting.

**Project: a kernel you broke on purpose.**

1. Clone the stable tree, `make defconfig`, build, and boot it under QEMU with a BusyBox initramfs you assembled yourself. Script the whole thing: `make run` should rebuild and boot in one command. Keep this harness; every later unit uses it.
2. Move the `/dev/pipe0` driver in-tree under `drivers/char/`, add it to Kconfig and the Makefile, build it as `=y` and `=m`, and verify both.
3. Enable KASAN, UBSAN, lockdep, and `DEBUG_ATOMIC_SLEEP`. Reintroduce each Unit 3 bug (use-after-free, sleeping under spinlock, lock inversion) one at a time and collect the report each tool gives. Decode each trace back to a source line with `faddr2line`.
4. Attach gdb to the running QEMU kernel, set a breakpoint in your `read` method, trigger it from a shell inside the guest, and walk the stack back into the VFS. This is the moment the whole stack becomes one program.
5. Use `ftrace` function graph tracing to record everything the kernel does during one `write()` to your device, and annotate the trace in a short write-up.

**Exit check.** From a raw oops pasted into a text file, you can identify the faulting function, the line, the context (interrupt or process), and a plausible cause, in under ten minutes.

## Unit 5 — The driver model, buses, and device tree

Real drivers do not create devices; the kernel discovers hardware and hands matching devices to drivers. This unit is the bus/device/driver triangle and the probe/remove lifecycle, which is the shape of every modern driver in the tree.

**Concepts.** `struct device`, `struct device_driver`, `struct bus_type`, and the matching rules. The platform bus for memory-mapped, non-discoverable hardware. `probe`/`remove` and `devm_` resource management (why `devm_kzalloc`, `devm_ioremap_resource`, and friends exist, and when they are wrong). Device tree: `.dts` source, bindings in YAML, `compatible` strings, `of_match_table`, reading properties with the `of_*` and `device_property_*` APIs. `MMIO`: `ioremap`, `readl`/`writel`, and why you never dereference a device pointer directly. The `regmap` abstraction. How I²C, SPI, and USB each specialize the model (`i2c_driver`, `spi_driver`, `usb_driver`). Kernel subsystems as frameworks: your driver registers with IIO, input, GPIO, or a similar subsystem, which owns the userspace interface.

**Reading.** `Documentation/driver-api/driver-model/` (all of it). `Documentation/devicetree/usage-model.rst` and `bindings/writing-schema.rst`. Bootlin's slides, sections on the device model, device tree, and platform drivers — the best single source for this unit. LDD3 chapter 14 (concepts only; the API has moved). `drivers/misc/` and `drivers/iio/` as reading material: pick three small drivers and trace `probe` end to end.

**Project: a virtual platform device bound by device tree.**

1. Switch the QEMU harness to `aarch64` with the `virt` machine; dump its device tree (`dtc -I dtb`) and read it until it makes sense.
2. Add a node for an invented device, `acme,pipe-ctrl`, to a `.dts` overlay with a `reg` range and a couple of properties (buffer size, a mode flag). Write a YAML binding for it and validate it with `dt_binding_check`.
3. Write a platform driver with an `of_match_table` that matches it. In `probe`, read the properties, `devm_ioremap` the register range (it will be unbacked memory on `virt`; that is fine), and create the Unit 2 char device from the device-tree properties instead of module parameters. Handle `remove` and `-EPROBE_DEFER` correctly.
4. Register the same driver with a real subsystem instead of a raw char device: expose your buffer's fill level as an IIO channel, or a mode flag as a GPIO line. Observe how much userspace interface the subsystem gave you for free.
5. Stretch: write a second driver for the same `compatible` string as an I²C client driver, with the device attached to QEMU's I²C controller, and reuse the core logic between the two through a small shared "core" module.

**Exit check.** You can draw the bus/device/driver relationship and show, for one device in `/sys/bus/platform/devices/`, which struct each sysfs entry comes from. You can explain why `devm_` resources are freed in reverse order and what that means for ordering in `probe`.

## Unit 6 — Interrupts, deferred work, and time

Hardware talks to the kernel by interrupting it, and an interrupt handler runs in the most restricted context there is. The whole unit is about doing as little as possible in the handler and deferring the rest correctly.

**Concepts.** `request_irq`/`devm_request_irq`, handler return values, shared and threaded interrupts (`request_threaded_irq` and why the threaded half is usually what you want). Top half versus bottom half: softirqs, tasklets (deprecated; know why), workqueues (`work_struct`, `delayed_work`, the system queues versus your own). What you may and may not do in each context, and how that interacts with the Unit 3 locking rules (`spin_lock_irqsave`). Time: `jiffies`, `ktime`, `hrtimer`, `timer_list`, `msleep` versus `udelay`, and why busy-waiting is sometimes right. Wait queues revisited: waking a sleeping reader from an interrupt. Interrupt controllers and the `irq_domain`, briefly. DMA: coherent versus streaming mappings and `dma_map_single` (concepts; the project touches it only lightly).

**Reading.** LDD3 chapters 7, 10, and 15. *Linux Kernel Development* chapters 7, 8, and 11. `Documentation/core-api/workqueue.rst`, `genericirq.rst`, and `timekeeping.rst`. `Documentation/core-api/dma-api-howto.rst` for the DMA concepts.

**Project: an interrupt-driven device that does not exist.**

1. Give your `acme,pipe-ctrl` device an `interrupts` property in the device tree. QEMU's `virt` machine will not raise it, so write a tiny second module that injects interrupts for you on a timer — a fake device — or, better, write a minimal QEMU device model in C (QEMU's own `hw/misc/edu.c` is the template; this is optional but it is the most realistic path).
2. In the driver, replace the blocking-read wait with interrupt-driven wakeups: the handler acknowledges the "hardware," moves data into the `kfifo` in a threaded handler or workqueue, and wakes readers. Keep the hard handler to a handful of lines and prove it with `ftrace` timestamps.
3. Add a watchdog: a `delayed_work` that fires if no interrupt arrives for N ms, logs it, and resets the fake device. Expose the timeout through sysfs.
4. Hold a lock in both the handler and the `read` path and get it wrong (plain `spin_lock` in process context, interrupt arrives, deadlock). Watch lockdep's `HARDIRQ-safe -> HARDIRQ-unsafe` report, then fix it with `spin_lock_irqsave`.
5. Stretch: implement `poll`/`epoll` support properly and write a userspace program that services 100 reads a second with no busy-waiting, measuring latency from interrupt to userspace with `ftrace` or `perf`.

**Exit check.** For any line of your driver, you can name the context it runs in, what it is allowed to call, and what lock variant it must use. You can explain why a threaded IRQ handler can sleep and a hard one cannot.

## Unit 7 — Real hardware: a complete driver

Everything so far was against a device you controlled. A real part has a datasheet, timing requirements, errata, and a register map that lies occasionally. This unit produces a driver you could submit upstream.

**Concepts.** Reading a datasheet for what the driver needs: register map, power-up sequence, conversion timing, interrupt lines. Board bring-up: serial console, kernel on an SD card, device-tree overlays on a real board. The I²C subsystem in full: `i2c_client`, `i2c_driver`, SMBus helpers, `regmap_i2c`. The IIO subsystem: channels, `iio_info`, raw versus processed values, scale and offset, buffered capture with triggers. Power management: runtime PM, `suspend`/`resume` callbacks, regulators. Cross-compiling and deploying to a target. The unit is where `devm_`, `regmap`, DT bindings, and the subsystem framework all pay off at once.

**Reading.** Bootlin's slides, the I²C and IIO sections, and their free embedded Linux lab exercises (which use exactly this board-plus-sensor setup). `Documentation/driver-api/iio/` and `Documentation/i2c/`. The sensor's datasheet, read twice. Two existing drivers for similar parts in `drivers/iio/pressure/` or `drivers/iio/temperature/` — read them line by line before writing your own, and note what they do that the datasheet does not mention. `Documentation/power/runtime_pm.rst`.

**Project: an IIO driver for a cheap I²C sensor.**

1. Bring up the Pi with your own kernel build: cross-compile, boot from SD, serial console. Confirm the stock driver for your sensor works (`i2cdetect`, `/sys/bus/iio/`), then blacklist it. You are about to replace it.
2. Write the driver from the datasheet, not from the existing one: `i2c_driver` with an `of_match_table`, `regmap` for register access, `probe` that reads the chip ID and refuses the wrong part, IIO channels for each measurement with correct scale and offset so `iio_info` and `iio_readdev` show real-world units.
3. Add a device-tree overlay and binding so the device is discovered at boot with no manual `echo` into `new_device`.
4. Add buffered capture with the sensor's data-ready interrupt (or a `hrtimer` trigger if the part has none), and stream samples to userspace through the IIO buffer. Measure sample jitter.
5. Add runtime PM so the part sleeps when no one is reading, and verify current draw with a USB power meter if you have one.
6. Compare your driver with the in-tree one you blacklisted. Write up every difference and classify each as: you were wrong, they were wrong, or a judgment call. At least one should be a real bug or improvement in theirs — that is your Unit 8 patch.

**Exit check.** The driver is checkpatch-clean, probes from device tree, survives `rmmod` mid-capture, suspends and resumes, and you can defend every design choice in it against the in-tree driver's choices.

## Unit 8 — Contributing upstream

Upstream is where the skill becomes a credential. The process is email-based, slow, and exacting, and the first patch is mostly about learning the process; the technical content can be tiny.

**Concepts.** The development cycle: merge window, `-rc` releases, subsystem trees, `linux-next`. `MAINTAINERS` and `scripts/get_maintainer.pl`. Patch format: one logical change per patch, subsystem prefix, imperative subject, a body that explains why, `Signed-off-by` and what the DCO means. `git format-patch`, `git send-email`, cover letters, versioning (`v2`, changelog under the `---`). `checkpatch.pl` and `scripts/kernel-doc`. Reading mailing-list review and responding to it. `b4` for fetching and applying series from lore. Where newcomers are welcome: `drivers/staging/`, documentation, `Kconfig` help text, coccinelle-found cleanups, and the kernel's own TODO files.

**Reading.** `Documentation/process/submitting-patches.rst`, `development-process.rst`, `email-clients.rst`, and `submit-checklist.rst` — all required. `Documentation/process/kernel-docs.rst`. Greg Kroah-Hartman's talk *Write and Submit your first Linux kernel Patch* (video). The Linux Foundation's Kernel Mentorship Program materials, whether or not you apply.

**Project: one merged patch, then a real one.**

1. Configure `git send-email` and a plain-text-capable mail setup. Send yourself a patch and confirm it applies cleanly with `git am`. Most first-patch rejections are mail-client damage; eliminate that first.
2. Find a `drivers/staging/` driver with a `TODO` file, pick one checkpatch warning or one TODO item, fix it, run `get_maintainer.pl`, and send it. Respond to every review comment within a day. Iterate to `v2`, `v3` if asked. Get it merged into `staging-next`.
3. Send the Unit 7 finding (the bug or improvement in the in-tree sensor driver) as a proper patch to the IIO maintainers, with a cover letter that explains how you found it. This one is reviewed by people who do not know you and care about the subsystem; expect substantive pushback and treat it as the course's final exam.
4. Subscribe to the IIO or staging list for a month and review two other people's patches. Reviewing is how you learn what reviewers look for, and reviewed-by tags are credit in their own right.

**Exit check.** You have a commit in a maintainer's tree with your name on it, and a mailing-list thread in which you changed your mind in response to review.

## Capstone project options

Pick one after Unit 7. Each is large enough to be a portfolio piece and small enough to finish in two to three months of part-time work. All three end with code someone else could use.

| Option | What you build | What it exercises | Why it is a good credential |
| --- | --- | --- | --- |
| A. USB device driver | A driver for a cheap USB gadget with no in-tree support (a USB relay board, a vendor-specific HID device, a cheap logic analyzer). Reverse-engineer the protocol with Wireshark's USB capture, then write a `usb_driver` that exposes it through the right subsystem (input, GPIO, or a char device as last resort). | USB subsystem, URBs, protocol reverse-engineering, hotplug, a different bus from Unit 7 | It is real, it fills a real gap, and it is submittable upstream |
| B. Virtual device end to end | A QEMU device model in C (`hw/misc/`) for an invented DMA-capable PCI device, plus the Linux driver for it: PCI probe, BAR mapping, MSI interrupts, DMA ring buffers, a `/dev` interface, and a userspace test suite. | PCI, DMA mapping API, MSI, the QEMU side of the hardware contract | Shows you understand both sides of the hardware boundary — rare and valued at chip vendors |
| C. A small filesystem or block driver | Either a RAM-backed block device with a proper `blk-mq` request queue and `mkfs`/`mount` working on it, or a tiny read-only filesystem (think 300 lines) mounted from an image you generate with a Python tool. | The block layer or the VFS from the other side, `bio`/request handling, superblock/inode/dentry | Demonstrates systems depth beyond "driver for a sensor" |

Whichever you choose, finish with three artifacts: the code in a public repo with a README that explains the design; a write-up (blog post or long README section) of the two hardest bugs and how you found them; and at least one patch upstream that came out of the work, even if it is a documentation fix.

**Keep in view as you go.** Rust in the kernel is real and growing (`Documentation/rust/`); once you are through Unit 5, read a Rust driver in the tree alongside its C equivalent. The C concepts in this syllabus are exactly what Rust's ownership model is formalizing, and reading both makes each clearer.

**Two habits for the whole course.** Keep a lab notebook: one entry per session with what you tried, what broke, and the exact error text. And read one real driver per week from the tree, start to finish, even when it is above your level — the pattern-matching this builds is most of what senior kernel engineers have that beginners do not.
